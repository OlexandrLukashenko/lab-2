# Лабораторна робота №2 — Об’єкти, прототипи та this: модель сутностей

## Тема
Продовження гри **FPV Drone Arena** з лабораторної роботи №1. У цій роботі базовий стан дрона перенесено з простого об’єкта до моделі сутностей на основі `class`, наслідування, композиції, `Map` і `Set`.

## Мета
Практично дослідити об’єкти як набір властивостей, `class`, один рівень `extends`, правила `this`, стрілкові функції, композицію, `Map`/`Set`, колізії та керування життєвим циклом ігрових сутностей.

## Запуск
```bash
npm install
npm run dev
```
Після запуску Vite відкрити адресу, яку покаже термінал.

## Керування
- `WASD` або стрілки — рух дрона.
- `SPACE` — звичайний постріл.
- `H` — homing-постріл.
- `F` — альтернативний виклик `fire()` через стрілкову функцію.
- `ESC` — примусовий респаун після знищення.

## Архітектура

```text
Vector2
  ↓
Entity
  ├── Ship
  ├── Bullet
  ├── Asteroid
  ├── Pickup
  └── Particle

World
  └── Map<id, Entity>
       ↓
CollisionSystem
       ↓
Renderer / HUD
```

`Ship` є єдиним прямим нащадком `Entity`, як вимагає завдання. Інші сутності також наслідують `Entity`, але дерево не поглиблюється.

## Vector2
`Vector2` містить чисті методи `add`, `sub`, `scale`, `normalized`, `distanceTo`. Вони повертають новий вектор і не змінюють аргументи. Це дозволяє уникати прихованої мутації стану під час фізичних розрахунків.

## Entity
Базова сутність містить:

- приватний лічильник `Entity.#nextId`;
- приватне поле `#id`;
- `position`;
- `velocity`;
- `radius`;
- `kind`;
- `dead`;
- метод `update()`.

Ідентифікатор доступний через getter `id`, але приватний лічильник недоступний зовнішньому коду.

## Ship
`Ship extends Entity` має приватне поле `#hp` і публічний `get hp()`.

Метод `fire(world)` створює кулю з носа корабля. Початкова швидкість кулі складається зі швидкості пострілу та поточної швидкості корабля.

## World та Map
Усі сутності зберігаються у:

```js
Map<id, Entity>
```

World підтримує:

- `spawn(entity)`;
- `despawn(entity)`;
- ітерацію через `[Symbol.iterator]`;
- генератор `ofKind(kind)`;
- `step(dt)`;
- `sweep()`.

Видалення реалізоване через два етапи: сутність спочатку отримує `dead = true`, а наприкінці кроку `sweep()` прибирає її з `Map`.

## Кулі та TTL
Куля має `ttl`. На кожному `update()` TTL зменшується. Після досягнення нуля куля позначається мертвою. Це не потребує миттєвої модифікації `Map` під час її ітерації.

## Колізії
Колізії винесені в окрему систему `CollisionSystem.js`.

Для двох кіл перевіряється:

```text
distance(centerA, centerB) <= radiusA + radiusB
```

Реалізація свідомо використовує наївний `O(n²)`, оскільки для невеликої кількості сутностей це достатньо просто та прозоро для лабораторної роботи.

Кулі можуть влучати в:

- корабель;
- астероїди.

Після знищення створюється вибух із частинок і збільшується рахунок.

## Респаун
При зниженні `hp` корабля до нуля корабель позначається мертвим, створюється вибух і запускається таймер респауну на **2 секунди**.

## this: чотири правила

### 1. Виклик як методу
```js
ship.fire(world);
```
Тут `this` всередині `fire()` посилається на `ship`.

### 2. Виклик як звичайної функції
```js
const fire = ship.fire;
fire(world);
```
Метод втрачає контекст об’єкта. У strict mode `this` буде `undefined`.

### 3. Явне встановлення через bind/call/apply
```js
const fire = ship.fire.bind(ship);
fire(world);
```
`bind()` назавжди прив’язує `this` до конкретного корабля.

### 4. Конструктор
```js
new Ship(position)
```
Під час створення екземпляра `this` посилається на новий об’єкт.

### Стрілкові функції
Стрілкова функція не створює власний `this`, а використовує `this` із зовнішнього lexical scope. Тому callback можна оформити так:

```js
const fireWithArrow = () => ship.fire(world);
```

У цій лабораторній використано стрілковий callback для альтернативного виклику `fire()`.

## Прототипний ланцюжок
Один експеримент можна виконати в консолі браузера:

```js
const ship = [...world.ofKind("ship")][0];
Object.getPrototypeOf(ship) === Ship.prototype;
Object.getPrototypeOf(Ship.prototype) === Entity.prototype;
Object.getPrototypeOf(Entity.prototype) === Object.prototype;
```

Це показує короткий прототипний ланцюжок:

```text
ship
 ↓
Ship.prototype
 ↓
Entity.prototype
 ↓
Object.prototype
 ↓
null
```

Глибше дерево наслідування для гри не потрібне.

## Композиція замість глибокої ієрархії

Уявна ієрархія могла б виглядати так:

```text
Entity
└── Projectile
    ├── NormalBullet
    └── HomingBullet
```

А для бонусів:

```text
Entity
└── Collectible
    ├── HealPickup
    └── ShieldPickup
```

Такий підхід швидко породжує багато класів, особливо якщо одна сутність повинна мати кілька властивостей одночасно.

Тому використано композицію.

### Homing
`Bullet` має властивість:

```js
homing: true
```

та у `update()` може виконувати наведення на астероїд. Для створення homing-поведінки не потрібен окремий `HomingBullet extends Bullet`.

### Pickup
`Pickup` має дані:

```js
type: "heal"
```

Колізійна система знає, що pickup можна зібрати кораблем, а сам pickup виконує свою дію через `collect(ship)`.

Таким чином, поведінка комбінується властивостями та окремими системами, а не глибоким деревом класів.

## Set
У `input.js` використовується:

```js
const keys = new Set();
```

`Set` зручно зберігає набір натиснутих клавіш без дублювання. `add()` виконується при натисканні, `delete()` — при відпусканні, `has()` — під час перевірки стану.

## Збереження fixed timestep з Лаби №1
Ігровий цикл з `requestAnimationFrame` зберігається. Фізика та оновлення світу виконуються з фіксованим `dt = 1/60`, тому логіка гри не залежить безпосередньо від FPS монітора.

## Висновок
У лабораторній роботі №2 базову гру FPV Drone Arena розширено моделлю об’єктних сутностей. Використано `class`, один рівень наслідування для корабля, приватні поля, getter, `Map`, `Set`, генератор, життєвий цикл `spawn/despawn/sweep`, систему колізій, TTL, частинки, респаун та HUD. Для homing і pickup використано композиційний підхід, що дозволяє не створювати глибоку ієрархію класів.
